# План реалізації сайту

Цей план перетворює [вимоги власника](product-requirements.md) на послідовні етапи роботи. Він описує порядок і перевірку результату, без вигаданих строків. Поточний стан функцій ведеться в [дорожній карті](roadmap.md).

## Принцип роботи

Кожен етап завершується перевіркою повного шляху: редактор зберігає та публікує дані в Strapi → API повертає їх → відвідувач бачить правильний результат на сайті. Зміни моделі CMS робити після резервної копії локальної бази та завантажених файлів. Демонстраційний вміст не повинен підміняти порожню відповідь справної CMS.

| --- | --- | --- |
| 0 | Основа для розробки | Зафіксувати залежності `frontend/` і `cms/`, описати резервне копіювання даних Strapi, перевірити локальні `build` і запуск. Відокремити помилку API від порожнього списку. |

Для постійного запуску вибрати домен школи або власний платний домен. |

## Найближчий робочий зріз

Знімок демонстраційної бази та фото вже додано до Git; версії залежностей зафіксовані в lockfile. Події, календар, головна й сторінка «Про нас» реалізовані в коді. Локалізацію Strapi та React увімкнено зі збереженням українського вмісту; редактору залишається наповнити англійські переклади. Перегляд PDF та автоматичну конвертацію DOC/DOCX реалізовано в коді; наступний крок — перевірити по одному реальному файлу кожного формату через адмінку.

## Рішення під час реалізації

- **Мовні адреси:** поточна сторінка зберігається під час перемикання; `?lang=uk` і `?lang=en` дають прямі посилання на обрану мову. Для іншомовного slug події відповідник знаходиться за `documentId`.
- **Переклад контенту:** назви, описи й основні тексти перекладає редактор; дати, категорії та медіа варто спільно використовувати там, де це підтримує модель. Автоматичний переклад не входить до вимог.
- **Перегляд DOC/DOCX:** зробити коротку перевірку обраного способу на реальних файлах перед зміною моделі документів. Саме посилання на файл не задовольняє вимогу перегляду на сайті.
- **Розгортання:** перед публічним запуском визначити хостинг, постійне сховище бази й медіа, резервне копіювання та домен/API. Це окреме рішення після перевірки локальної версії.

## Пізніші етапи

1. **FUT-02 — розклад:** погодити шаблон CSV, правила валідації та оновлення, зробити попередній перегляд імпорту; далі додати фільтри за класом, предметом і вчителем.
2. **FUT-01 — 3D-тур:** після отримання матеріалів туру визначити формат, місце на сайті та спосіб вбудування.

Після завершення кожного етапу оновлювати [дорожню карту](roadmap.md), [архітектуру](architecture.md) та [довідник CMS](content-management.md), якщо відповідні частини змінилися.
