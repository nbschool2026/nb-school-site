# Плани розвитку

Цей файл зберігає стан розвитку сайту в репозиторії. Детальні критерії готовності для семи пунктів власника наведено у [функціональних вимогах](product-requirements.md). Порядок у таблиці не задає строків чи пріоритетів.

## Підтверджені потреби

| Напрям | Стан | Що потрібно уточнити / зробити |
| --- | --- | --- |
| Події: список, сторінка події, фото, YouTube | Частково | EVT-01 у [вимогах](product-requirements.md#evt-01--список-і-сторінка-події) |
| Категорії та календар, спільна фільтрація | Частково | EVT-02 — EVT-04 у [вимогах](product-requirements.md) |

| Історія та вчителі через CMS | Частково | ABOUT-01 у [вимогах](product-requirements.md) |
| Головне фото, контакти, чотири останні події через CMS | Частково | HOME-01 у [вимогах](product-requirements.md) |

| Документація в репозиторії | Створено | Підтримувати README і `docs/` разом зі змінами коду та контент-моделей |

## Виявлені прогалини

Це результати огляду коду, а не погоджений порядок робіт:

- Кнопки UA/EN не перемикають мову; моделі CMS одномовні.
- Деякі тексти, контакти, зображення та календар подій жорстко задані у React. Календар показує травень 2026 року незалежно від поточної дати.
- Параметри класу, предмета й учителя в блоці розкладу поки не фільтрують уроки.
- Якщо API повертає порожній список, сайт показує демонстраційний fallback-контент. Це може приховати відсутність опублікованих записів.
- Модель галереї існує в CMS, але не виводиться на публічному сайті.
- Частина стартових записів має прикладовий характер і потребує звірення з фактичними даними школи.
- Для розгортання поза локальним комп'ютером потрібно визначити зберігання бази, медіа, резервні копії та адреси API/CORS.

## Наступні ідеї

Сім поточних пунктів уже внесено до [вимог](product-requirements.md). Нові ідеї додавайте нижче або оформлюйте окремою GitHub issue з посиланням звідси. Для кожної достатньо короткого опису; деталі можна доповнити перед реалізацією.

### Шаблон

```text
Назва:
Для кого і яку задачу вирішує:
Де з'явиться на сайті:
Який вміст має редагуватися в CMS:
Що означає «готово»:
Статус: ідея / заплановано / у роботі / готово / відкладено
```

## Правило оновлення

Коли функцію починають розробляти, запишіть у цьому файлі її мету та критерій готовності. Після реалізації оновіть статус, [архітектуру](architecture.md), [моделі контенту](content-management.md) й команди запуску, якщо вони змінилися. Не позначайте функцію готовою лише за наявністю кнопки чи схеми CMS: перевіряйте повний шлях від редагування в адмінці до відображення на публічному сайті.
